# Audit 09: project opening and kind detection

## P1 `src/lib/lsp/rootSignals.ts:27` root_signals do not mirror the Rust detector's build/compile_commands search

`probeRootSignals` only reads the root directory's direct entries (`Cargo.toml`, `compile_commands.json`, `CMakeLists.txt`). The Rust `detect` in `src-tauri/src/project/cargo_manifest.rs:70-101` also finds `build/compile_commands.json`, walks ancestors, and descends two levels. Result: a C/C++ project opened at its source root whose `compile_commands.json` lives only under `build/` (common out-of-source layout) reports `hasCompileCommands: false`; if it also has no top-level C++ files in the scanned tree, `serversForRoot` in `src/lib/lsp/served.ts:52` never starts clangd even though `inspect()` classified the project as `CompileCommands`. The LSP pane is dead while the Run/Debug pane may still prefilled. Fix: make `probeRootSignals` honour `build/compile_commands.json` (and, ideally, the same ancestor/descend rules) so the frontend's `running` set matches the Rust kind.

## P1 `src-tauri/src/project/cargo_manifest.rs:21-36` opened subdirectory keeps its own path as `root`

`inspect` canonicalises the opened path and stores it as `ProjectInfo.root` even when `detect` resolved the manifest in an ancestor. For a user opening `crates/foo/src`, `root` becomes `…/src` while `build_root` becomes `…/crates/foo`. The shell then uses `project.root` for LSP (`src/ui/app/useShell.ts:52`) and file trees, while builds use `build_root`; rust-analyzer is probed against `src/` which has no `Cargo.toml`, so it does not start. Either constrain opening to the detected root, or report the detected root as `root` and keep an `openedPath` separate. Fix: set `root` to the detected manifest directory (or expose both) and start LSP from `build_root`.

## P2 `src-tauri/src/project/descend.rs:38-47` `MAX_DEPTH = 2` misses deeper crates; silent `None` on permission errors

`descend` searches only two levels and swallows every `read_dir`/`canonicalize` failure as "missing". A crate at `a/b/c/Cargo.toml` is reported `Unknown` with no message, and a unreadable directory is treated identically. The failure the user sees is "no build system" / dead Run and Debug, indistinguishable from a genuinely empty project. Fix: either raise depth or make the limit explicit in the error, and return an error (or at least a distinct `Unknown` reason) instead of silently dropping I/O errors. (The `SKIP_DIRS` list at `descend.rs:19-27` also drops any marker inside a directory named `build`, `out`, `dist`, `target`, etc.; a `build/Cargo.toml` that is a real (unlikely) source layout is ignored.)

## P2 `src/lib/lsp/rootSignals.ts:25` global cache is never invalidated

`cache` is a module-level `Map<string, Promise<RootSignals>>` keyed only by root string and cleared only on rejection. If a project's files change between openings (added `Cargo.toml`, regenerated `compile_commands.json`), the stale promise is reused and the wrong server set starts. Fix: key the cache on root plus a cheap fingerprint (directory mtime / listing hash), or drop entries on project close.

## P3 `src-tauri/src/project/cargo_manifest.rs:96` a workspace root with no `[package]` has no name

`cargo_package_name` returns `None` for a pure `[workspace]` manifest, so `inspect` falls back to `directory_name`. That is defensible, but the fallback never says so; a root named `workspace` shows up as the project name. Combined with `launch_config: None` for any root without `.quarry/launch.json`, the status bar/name area gives no hint that the crate is a workspace with N members. Fix: detect `[workspace]` and append a small marker, or resolve the first member's name. (Informational only; no wrong behaviour beyond labelling.)

## P3 `src-tauri/src/project/cargo_manifest.rs:80-99` CMake root whose build dir is elsewhere is typed `CompileCommands`, not `Cmake`

When the opened root has `compile_commands.json` (or `build/compile_commands.json`) but no `CMakeLists.txt`, `detect` returns `CompileCommands`. A CMake project opened from its build directory therefore loses `cmake_target()` parsing (`src-tauri/src/launch/default_cpp.rs:74`), so the launch target falls back to the directory name and `cpp_executables` probes conventional paths. The user sees a generic target named after the build dir instead of the CMake target. Fix: search ancestors for `CMakeLists.txt` before trusting `compile_commands.json`, or record the source root alongside.

## Checked, no issue

- `detect_ancestors` priority (`Cargo.toml` > `CMakeLists.txt` > `compile_commands.json` > `build/compile_commands.json`) matches the documented order; `tests_items.rs:67` and `tests_descend.rs:119` confirm root wins and priority. No change needed.
- A missing root returns `cannot open project root …: No such file` (`cargo_manifest.rs:23`); `tests_items.rs:108` covers the `does-not-exist` substring. No wrong message found there.
- `launch_config_path` (`unquote.rs:74`) correctly reports absence as `None`; `tests_items.rs:124` covers presence. No false-positive claim of a config.
- `rootSignals` scan caps (`MAX_DEPTH = 4`, `MAX_DIRS = 64`) and skipped dirs are tested (`rootSignals.test.ts:39-99`); behaviour is intentional and consistent with the documented bounds.
- `decideRootSignals` is pure and deterministic (`rootSignals.ts:10-16`); no branching bug found in the decision itself.

## Cache behaviour

- `rootSignals.ts:25` keeps one `Promise` per root string for the whole page lifetime. `probeRootSignals` returns the cached promise on second call; there is no eviction and no re-scan when the directory changes (`rootSignals.ts:27-48`). Consequences:
    - A marker added after open (new `Cargo.toml`, regenerated `compile_commands.json`, first `.cpp` file) does not change `signals`, so `useLspServers` (`src/lib/lsp/session.ts:118-156`) never enables a new server. The tree and outline stay without that server until a full reload.
    - Restart does not help: `restartToken` (`session.ts:120`) re-runs `startLsp` only for kinds already in `serversForRoot(signals)`; it does not recompute `signals`.
    - The only way out is closing the project and reopening it, and even then the module-level cache can survive across opens if the root string is identical (`rootSignals.ts:27-31`). A reload of the app is required to clear it.

## Wrong rows and smallest fix

- `build/compile_commands.json` at root → `CompileCommands` in Rust but `hasCompileCommands: false` in TS: `src/lib/lsp/rootSignals.ts:40` must also stat `build/compile_commands.json` (mirror `cargo_manifest.rs:94-99`), or better, ask Rust for the same probe.
- Monorepo with sibling crates at depth 1 and no root manifest → `Unknown`: `descend.rs:55-57` returns `Ambiguous`. If the expected shape is a workspace, require a root `Cargo.toml`; otherwise accept the first marker at depth 1 instead of `None`.
- Subdirectory open keeps `root = subdir`: `cargo_manifest.rs:27-36` sets `root` from the input before detection. Smallest fix is to return the detected directory as `root` when detection lands in an ancestor, or add `build_root`-based LSP startup in `useShell`.
- Deeper-than-two crates → `Unknown`: raise `MAX_DEPTH` in `descend.rs:43` (and update tests) or remove the bound for a one-time downward scan.
- Stale cache after file changes: delete the cache entry on project close, or key on a directory fingerprint.
